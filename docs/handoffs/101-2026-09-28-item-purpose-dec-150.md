## What was decided and what was built.

The owner asked whether the stock items that back a sellable can be separated
from those that do not, **with a term**, since both can be stocked and tracked
but are not the same kind of thing. Answer recorded as `DEC-150`:

- Umbrella **Stock items**; **for-sale** (a sellable is fulfilled from it —
  today's `finished_good`) vs **for-use** (an input consumed by
  production/operations; no variant may reference it).
- The distinguishing axis cannot be stocking or tracking (both apply to both
  sides); it is **purpose**. The sellable identity stays `Product`/
  `ProductVariant` (`DEC-030`); a variant is fulfilled from **zero or one**
  for-sale stock item, so a made-to-order sellable has none.
- Implemented as **data, not a type mapping** (`item.purpose`, migration `0079`,
  expand-only + down): added nullable, backfilled
  `CASE WHEN item_type='finished_good' THEN 'for_sale' ELSE 'for_use' END`, then
  `NOT NULL`/`DEFAULT 'for_use'` + `for_sale|for_use` check + an
  `(organization_id, purpose)` index. Editable afterwards because exceptions are
  real (a staff-meal finished good is for-use; an intermediate sold as a product
  is for-sale).
- **Edge guard** `product_variant_finished_good_purpose_guard` (`ERRCODE 23514`,
  forward-only, skips an unchanged id and a missing row): a variant may reference
  only a **for-sale** item in its own organization; the variant commands raise
  the friendly `DomainError` first.
- UI: nav **Stock**, page **Stock items**, **All / For sale / For use** tabs with
  counts, a **Purpose** badge on the register, the item form prefilled with the
  derived default, the variant's finished-good picker limited to for-sale items
  and labelled **Stocked from**, the variant view showing "Stocked from", and
  **Backs** on the item view (new `listVariantsByFinishedGoodItem` read).

## Deferred / recorded.

- **Backfill assumption:** every existing `finished_good` is for-sale and every
  other type is for-use; an operator should re-classify any wrong row on the
  Stock screen. Pre-existing variant links are **not** revalidated (the guard is
  forward-only).
- The DB default is `for_use` for a raw-SQL insert of a `finished_good` (app
  paths derive correctly); import paths must set the purpose explicitly.
- `ITEM_PURPOSE` lives in `packages/persistence/src/schema/catalog.ts` rather than
  `vocabularies.ts` (the `vocabularies.test.ts` yaml-parity guard needs a matching
  `schemas/domain-enums.yaml` key, which was out of scope here). Small follow-up:
  add `item_purpose: [for_sale, for_use]` to the enum file and move the array
  next to `ITEM_TYPE`/`INVENTORY_POLICY`.
- `0079`'s backfill `UPDATE` and `SET NOT NULL` are table rewrites by nature — on
  a large catalog run them in the deploy window.
